## A stale clone, and how it got caught

The run started against a `par-build` clone 16 commits behind. On that code the baseline
was pinned (`VENUE_SCRAPE_FILE = {"stow": "_scrape_stow_20260815.json"}`) and the local
copy of that file predated last week's upload.

Scraped live pars before touching anything and diffed them against the model's
`current_par`: **50 SKUs disagreed**. Re-checking the 52-row raise payload against live
gave 21 genuine raises, 23 no-ops, and **8 rows that were actually cuts** — cuts sitting
in the raise payload, so they had bypassed `build_decreases.py` and its zero-delisting and
weeks-of-cover checks.

Uploaded only the 21-minus-1 that were genuine raises vs live, and withheld every
decrease, on the grounds that a decrease is the direction that can cause a stockout and
these had been scored against the wrong baseline.

Then pulled `origin/main` properly. Upstream had already fixed both halves of this:

- `6890397c par: the baseline is found, not pinned` — `VENUE_SCRAPE_FILE` now resolves to
  the newest `_scrape_<venue>_YYYYMMDD.json`.
- `f5c139c4 par: baseline = tonight's live-audited state` — the 15 Aug baseline was
  re-scraped post-upload and verified on-screen.

**The live scrape taken this morning matches upstream's audited 15 Aug baseline exactly —
0 differing values, 0 SKUs on either side alone.** Two independent scrapes agreeing is
the strongest confirmation available that the recorded par state is the real one.

Re-ran on the corrected code: **21 raises, and every value matched what had been uploaded**.
`build_decreases.py` then reclassified the 8 mislabelled cuts correctly, checked them, and
cleared all 10 decreases with 1.7-2.8 weeks of cover remaining — so those were applied too.

Nothing here is an open defect. It was a stale working copy, and the guard that caught it
was scraping live state before trusting the model's idea of it. Worth keeping as the first
step of every run.
